# Принятые решения

Короткие ADR. Эти решения уже приняты: Claude Code их не пересматривает без явного запроса.
Этот файл также можно перенести в README и использовать как шпаргалку к видео-ревью.

## 001. Оптимистичная конкурентность через `xmin`

**Решение:** `public uint Version { get; set; }` + `.IsRowVersion()`. Npgsql мапит это на системную колонку PostgreSQL `xmin`.

**Почему:** в PostgreSQL нет типа `rowversion`, как в SQL Server. `xmin` меняется при каждом UPDATE строки, EF Core добавляет его в `WHERE` при сохранении. Если строку уже изменили, UPDATE затронет 0 строк, и EF бросит `DbUpdateConcurrencyException`.

**В `/complete` две проверки:**
- `IsCompleted == true` → 409: второй запрос пришёл уже после коммита первого.
- `DbUpdateConcurrencyException` → 409: настоящая гонка, оба запроса прочитали задачу незавершённой.

**Отвергнуто:** `SELECT ... FOR UPDATE` (пессимистичная блокировка) — держит транзакцию и блокировку, хуже масштабируется; в задании прямо просят «без локов». Ручная колонка `Guid ConcurrencyStamp` — работает, но требует обновлять её вручную.

## 002. Публикация через in-memory очередь `Channel<T>` + `BackgroundService`

**Решение:** эндпоинт вызывает `Enqueue()` (`TryWrite`), который возвращается мгновенно. Один фоновый сервис читает очередь и публикует в RabbitMQ.

**Почему:**
- HTTP-ответ не ждёт сеть и брокер (требование «без блокировки»).
- Один читатель, потому что `IChannel` в RabbitMQ.Client не потокобезопасен для параллельных публикаций. Так обходимся без локов и пула каналов.
- Очередь даёт естественную точку для graceful shutdown (см. 004).

**Компромисс:** очередь в памяти, при падении процесса её содержимое теряется. Канал bounded (например, 10 000) с `FullMode = DropOldest` и логом, чтобы при долгой недоступности брокера не вырасти по памяти бесконечно.

**Отвергнуто:** `Task.Run(() => Publish())` (fire-and-forget) — нет контроля над завершением, нельзя корректно дождаться при остановке, исключения теряются.

## 003. Публикация только после `SaveChangesAsync`; сбой брокера не валит запрос

**Решение:** порядок «сохранили в БД → поставили событие в очередь». Ошибки RabbitMQ ловятся в фоновом сервисе, логируются с `TaskId`, сообщение отбрасывается.

**Почему:** если публиковать до сохранения, а БД упадёт, подписчики получат событие о том, чего не было. Обратный риск (сохранили, но не отправили) меньше и честно описан как HACK.

**Как доделал бы:** Transactional Outbox — запись события в таблицу `outbox` в той же транзакции, что и обновление задачи, плюс фоновый relay, который отправляет и помечает отправленное. Это даёт at-least-once без потерь.

## 004. Graceful shutdown

**Решение:** в `StopAsync`:
1. `Writer.Complete()` — новые события больше не принимаются.
2. Ждём, пока читатель дослушает очередь, но не дольше 5 секунд.
3. `CloseAsync` канала → `CloseAsync` соединения → Dispose.

`HostOptions.ShutdownTimeout = 10s`, чтобы хост не прибил сервис раньше наших 5 секунд.

**Подвох:** `stoppingToken` из `ExecuteAsync` отменяется в начале остановки. Если передать его в `ReadAllAsync`, чтение оборвётся сразу и очередь не дочитается. Поэтому цикл чтения завершается по `Writer.Complete()`, а таймаут контролируется отдельно.

## 005. Интеграционный тест на Testcontainers

**Решение:** реальные PostgreSQL и RabbitMQ в контейнерах, приложение через `WebApplicationFactory<Program>`. Тестовый потребитель объявляет временную очередь и биндит её на `task.events`/`task.completed` до вызова API.

**Почему:** проверяем реальный путь сообщения, включая сериализацию и routing key, а не только факт вызова метода.

**Запасной вариант:** если Docker недоступен или не хватает времени — подменить `ITaskEventPublisher` фейком, собирающим события в список (спецификация это явно разрешает).

## 006. Простота структуры

**Решение:** один web-проект, файлы по ответственности, без слоёв Application/Domain/Infrastructure, без репозиториев поверх EF Core.

**Почему:** четыре эндпоинта и одна сущность. `DbContext` уже является репозиторием и unit of work; лишние слои увеличили бы объём кода, который нужно защищать, без пользы для задачи.

## 007. dotnet-claude-kit используется выборочно

**Решение:** из кита берём workflow (`/plan`, `/tdd`, `/migrate`, `/build-fix`, `/verify`, `/code-review`, `/checkpoint`) и практики, совпадающие со спекой (`TimeProvider`, `TypedResults`, ProblemDetails, Testcontainers, `IEntityTypeConfiguration`, `sealed`, `CancellationToken`). Дефолты, которые противоречат спеке, отключены в CLAUDE.md (таблица Override).

**Почему отключено:**
- .NET 10 / C# 14 — спека фиксирует .NET 9.
- Wolverine/MassTransit — проверяющий смотрит, как я сам публикую в exchange и закрываю соединение при остановке. Фреймворк спрятал бы ровно то, что оценивается.
- FluentValidation, Result pattern, хендлеры, `IEndpointGroup`, `/scaffold` — для 4 эндпоинтов это лишний код и лишняя косвенность. Спека прямо разрешает валидацию через `if`.
- Обязательная пагинация — спека требует вернуть все задачи; пагинация только как необязательный бонус.
- `/de-sloppify` удаляет TODO/HACK — а спека просит HACK-комментарии оставлять.

**Что сказать на ревью:** «Кит даёт хорошие дефолты для продакшен-проекта, но для тестового с жёстко заданным стеком я осознанно взял только то, что не противоречит требованиям».
